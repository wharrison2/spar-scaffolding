# Writing results
Writeups are to have a record of what was done, reports are for other people to see

## Writeups
 - Be concise but thorough. Write interpretations apart from results
 - Specify the path where outputs from a session went, and where any numbers in results stem from

## Reports/summaries
 - Avoid jargon
 - Keep this document useful as a standalone (but assume the reader has basic familiarity with the SDF dataset and the process to generate it)
 - Unless a data point is extremely important, do not repeat it in plain text. if precision is necessary, repeat it in a table. otherwise,
  leave it to the figures
 - Don't reference prior mistakes or other documents unless necessary. Do not mention your conversation with me except unless circumstances absolutely call for it
 - Never leave artifacts of the drafting or editing process (e.g. "not discussed further", "corrects an earlier statement", "pending check", "proposed and not applied"); write each report as if it were the only version the reader will ever see
 - Open with a brief methods section: what was measured, how, and over what. Put file paths and identifiers in one place at the end
 - Summary tables carry the takeaways, not statistics
 - Figures show the key comparison only: drop panels that don't carry the point, use colour to separate groups, and label bars with one readable value rather than raw counts
 - Give examples enough context to demonstrate the claim on their own: the setup, the surrounding text, and why it supports the point
 - Only put a finding in the main list if there is a credible story for why it matters; put the rest in a reference table
 - When citing validation or error rates, use the ones measured on the configuration that produced the results, not a range across versions
